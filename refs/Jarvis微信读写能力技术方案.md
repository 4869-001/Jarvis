# Jarvis 微信读写能力技术方案

## 1. 结论

Jarvis 当前可以安全地读取部分微信信息，但不应通过界面自动化直接发送个人微信消息。

- **读取能力**：只读 macOS 通知中心中由微信产生的结构化通知。
- **回复分析**：可以根据收到的通知生成摘要、分析和回复建议。
- **个人微信发送**：不自动执行，最后一步由用户在微信中完成。
- **可靠自动发送**：应使用企业微信、微信客服等提供联系人 ID、消息 ID 和发送回执的官方 API。

核心原因不是模型能力不足，而是个人微信客户端没有提供可验证的第三方读写接口。

> **2026-08-03 实施记录**：全自动发送（`wechat_send`）和备稿（`wechat_draft`）都实现并
> 实测过，最终**全部删除**，只保留 `wechat_read`。删除的直接原因见 §3.6：这台机器上
> 微信主窗口长期处于「窗口对象在、从未被合成绘制」的状态，四道校验关的第一关就永远
> 过不去，自动发送一次都没能走到第二关。本文其余分析依然成立。

## 2. 已验证的读取方案

Jarvis 不再使用截图或 OCR，也不注入微信进程。它读取 macOS 通知中心数据库中属于微信的结构化通知记录。

单条通知包含：

```text
UUID
发送人或会话名称
消息正文
时间
```

联系人和正文来自同一条原子记录，因此不会发生“联系人 A 配上消息 B”的视觉错配。

通知按照 UUID 去重，归档到：

```text
~/.jarvis/wechat/notifications.json
```

安全权限：

```text
~/.jarvis/wechat                     0700
notifications.json                  0600
```

### 读取能力边界

该方案只能读取：

- 产生过 macOS 通知的收到消息；
- 通知中包含的发送人、正文和时间；
- 开始归档之后仍能获得的通知记录。

不能读取：

- 用户自己发出的消息；
- 静音会话中没有产生通知的消息；
- 通知预览被系统或微信隐藏的正文；
- 归档启用前已经被通知中心清除的历史消息；
- 完整、双向的聊天数据库。

Jarvis 必须明确显示这些边界，不能把通知归档描述成完整聊天历史。

## 3. 开发过程中踩过的坑

### 3.1 OCR 和屏幕解读

早期方案从微信窗口截图并进行 OCR，尝试识别会话列表、未读徽标和当前聊天内容。

问题包括：

- 联系人、消息预览和正文位于不同视觉区域；
- 窗口缩放、滚动和主题会改变坐标；
- 遮挡和动画导致识别结果不完整；
- OCR 只能识别文字，无法证明两段文字属于同一个数据对象；
- 容易把联系人 A 与消息 B 拼接到一起。

结论：OCR 可以作为人工辅助识别，但不能作为可靠的微信消息数据层。

### 3.2 微信本地数据库解密

微信 4.1 的本地消息数据库采用 SQLCipher 加密。数据库密钥由微信进程持有。

尝试过的技术路径：

```text
task_for_pid
mach_vm_region
mach_vm_read_overwrite
扫描 WCDB 缓存密钥
```

实际阻碍：

- macOS SIP 开启时会拒绝读取微信进程内存；
- 即使使用 sudo，也可能被 task_for_pid 拒绝；
- 关闭 SIP 会扩大整台 Mac 的安全风险；
- 微信升级后数据库结构和密钥缓存形式可能变化；
- 密钥与解密后的聊天数据库都是高度敏感数据。

结论：不能要求普通用户关闭 SIP，也不能把进程内存扫描作为稳定产品能力。

### 3.3 macOS Accessibility

标准 macOS 应用通常会暴露按钮、文本框、列表项和选中状态。但微信聊天窗口主要是自绘界面。

实测只暴露了少量窗口级节点：

```text
关闭按钮
最小化按钮
全屏按钮
空的容器组
```

没有暴露：

- 当前联系人；
- 搜索结果；
- 会话选中状态；
- 消息输入框；
- 消息气泡；
- 发送状态。

结论：无法通过 Accessibility API 获得可靠的收件人和编辑框身份。

### 3.4 快捷键和坐标自动化

尝试过类似流程：

```text
激活微信
Command-F
输入联系人
选择搜索结果
进入会话
输入正文
Return
```

实际问题：

- 搜索后焦点可能仍停留在搜索栏；
- 第一个搜索结果不一定是目标联系人；
- 中文可能被输入法或键盘事件截断；
- 微信可能尚未加载搜索结果；
- 用户可能在流程中切换窗口或会话；
- 坐标随窗口尺寸、侧边栏宽度和系统缩放变化；
- Return 可能表示搜索、换行或发送；
- 输入框清空不等于消息发送给了正确联系人。

最严重的问题是：程序完成了键盘事件，并不代表微信完成了正确发送。

### 3.5 假成功状态

早期实现曾把以下条件误判为发送成功：

```text
键盘事件已提交
正文看似离开输入框
流程没有抛出异常
```

但微信没有返回：

```text
目标联系人 ID
消息 ID
服务器发送结果
可查询的发送状态
```

因此 Jarvis 可能显示“已发送”，而实际上消息没有发送，或者被发送到错误位置甚至错误联系人。

结论：没有消息 ID 和发送回执，就不能宣称发送成功。

### 3.6 窗口活着，但从未被绘制（2026-08-03 实测）

这是压垮自动发送的最后一根稻草，比前面几条更基本。

微信关掉窗口不退进程。此时：

```text
CGWindowList        报出一个 682×640、layer=0、onscreen=1 的窗口
Accessibility       报得出 window 1 的 position (125,217) 和 size
菜单栏               显示「微信」是前台应用
屏幕那块位置          画的是壁纸
```

也就是说，所有能查到的窗口元数据都说"窗口在那儿"，唯独像素不在。按这些坐标点下去，
点的是壁纸或压在下面的应用——实测点到过别的应用的菜单栏。

尝试过的恢复手段，全部无效：

```text
NSRunningApplication activateWithOptions:
open -a WeChat
点 Dock 图标（System Events）
点微信自己的「窗口 → 聊天」菜单项
```

唯一可靠的判据是**截屏幕区域做 OCR**（不是截窗口，那个被微信屏蔽），认不出微信界面
文字就说明它没画在那儿。这个判据本身是对的，也确实挡住了误点——但它在这台机器上
永远为假，自动发送因此一次都没能走到第二步。

结论：连"窗口在不在屏幕上"这种最基本的前提都无法稳定成立时，后面所有校验都没有
意义。自动发送不具备可运行的地基。

## 4. 为什么支持读，但不支持可靠写

### 读取

通知中心提供的是系统已经生成的结构化记录：

```text
微信通知记录
├── UUID
├── 发送人或会话
├── 正文
└── 时间
```

读取失败最多造成少读或无法读取，不会影响第三方，也不会向错误联系人发送内容。

### 写入

可靠发送至少需要：

```text
稳定且不可重名的联系人 ID
明确的目标会话 ID
确定性的发送接口
服务器返回的消息 ID
成功或失败回执
按消息 ID 查询或撤回的能力
```

个人微信客户端没有向 Jarvis 提供这些能力。

如果依赖昵称、窗口标题、搜索排序、焦点或坐标，就无法建立可靠的收件人验证链。

## 5. 安全实现路线

### 路线 A：企业微信或微信客服官方 API

这是推荐方案。

```mermaid
flowchart LR
    A[Jarvis 读取消息事件] --> B[使用稳定联系人 ID]
    B --> C[生成回复建议]
    C --> D[展示收件人与完整正文]
    D --> E[用户确认]
    E --> F[调用官方发送 API]
    F --> G[获得消息 ID]
    G --> H[查询并记录发送状态]
```

必须保留的数据：

```text
recipient_id
conversation_id
request_id
message_id
send_status
created_at
confirmed_by_user
```

只有收到官方成功回执后，Jarvis 才能显示“已发送”。

适用范围：

- 企业微信内部应用；
- 企业微信客户联系；
- 微信客服；
- 公众号客服消息；
- 其他微信官方开放平台允许的业务场景。

### 路线 B：个人微信的人机协作回复

如果必须使用个人微信，推荐让用户完成最后一步。这条路线也实现过（`wechat_draft`），
后来一并删除：把正文放进剪贴板再让用户自己粘贴，步骤比直接手打还多，没有净收益。
现在 Jarvis 只把拟好的回复作为普通文本回答给用户，不碰剪贴板、不碰微信界面。

Jarvis 可以：

1. 读取收到的微信通知；
2. 分析消息意图和上下文；
3. 生成多种回复建议；
4. 清楚显示目标联系人和正文；
5. 把用户选中的正文复制到剪贴板；
6. 打开微信；
7. 由用户亲自选择会话、粘贴并发送。

该方案自动化程度较低，但不会因为焦点、坐标或搜索排序错误而误发。

### 路线 C：微信内部插件或协议层

技术上可以通过注入微信进程、调用内部函数或模拟私有协议，尝试取得联系人 ID 和发送能力。

风险包括：

- 需要关闭或绕过 SIP、代码签名和运行时保护；
- 微信升级后函数偏移和内部协议可能失效；
- 存在风控、封号和数据安全风险；
- 可能违反微信软件许可或平台规则；
- 难以形成稳定、可维护、可审计的产品。

不建议作为正式产品路线。

## 6. 推荐产品架构

### 个人微信模式

```text
macOS 通知中心
        ↓
微信通知只读解析
        ↓
UUID 去重与本地归档
        ↓
Jarvis 摘要、分析、回复建议
        ↓
用户复制回复
        ↓
用户在微信中确认联系人并发送
```

### 官方 API 模式

```text
官方消息回调
        ↓
联系人 ID / 会话 ID
        ↓
Jarvis 分析和生成回复
        ↓
用户确认收件人与正文
        ↓
官方发送 API
        ↓
消息 ID 与发送回执
        ↓
审计日志和状态查询
```

## 7. 验收标准

### 读取能力

- 不使用截图或 OCR 关联联系人和正文；
- 单条消息必须具有原子 UUID；
- 联系人、正文和时间来自同一条结构化记录；
- 明确标注通知读取的覆盖边界；
- 私人内容只保存在本机受限目录；
- 每次内容进入模型前取得用户确认。

### 发送能力

只有同时满足以下条件才可上线自动发送：

- 使用稳定联系人 ID，而不是昵称；
- 能验证当前会话 ID；
- 使用确定性的发送接口，而不是键盘和坐标；
- 获得服务端消息 ID；
- 获得明确发送回执；
- 每次发送前展示收件人与完整正文；
- 支持审计、失败重试和状态查询；
- 不允许通用 auto-approve 绕过私人消息确认。

任何一项缺失，都只能生成草稿，不得宣称已经发送。

## 8. 当前 Jarvis 的最终边界

当前版本只有一个工具 `wechat_read`，保留：

- 微信通知只读；
- 未读数量与近期来信查询；
- 联系人和正文的原子关联（群聊另外给出群内发言人）；
- 本地通知归档；
- 最近来信分析；
- 回复建议生成（纯文本输出，不碰微信界面）。

当前版本删除（代码、工具注册、系统提示、构建依赖一并清理）：

- OCR 微信读取，以及 Vision / ScreenCaptureKit 依赖；
- 微信数据库进程内存扫描；
- SQLCipher 自动解密初始化；
- 微信快捷键与坐标自动发送；
- 窗口渲染校验、剪贴板抄回校验等一整套发送前校验；
- `wechat_send` 与 `wechat_draft` 工具；
- 未获得任何送达证据却显示“已发送”的逻辑。

最终原则：**读可以不完整，但必须真实；证明不了发给了谁，就一个字也不发。**
